# 生产商用门禁

当前 V2 已实现微信首发的主要运营流程，但尚未覆盖所有商业功能，也没有取得真实桩、真实资金和公网部署的完整上线验收结论。以下能力已落入代码：

- 微信小程序登录、管理端数据库账号登录、唯一超级管理员分配账号与租户 RBAC、访问/刷新令牌轮换与复用检测、账号锁定、首登/主动改密、即时会话撤销和身份数据留存清理。
- 平台超级管理员跨租户控制面和真实经营汇总，包括支付净收与支付机构实际分账的平台服务费。
- 场站、设备、端口、费率、订单、计量、停止、计费、微信支付/退款、双式账务、完整销售账单导入对账与结算核算；钱包余额查询及受审计人工更正；发票申请及真实开票凭证录入。
- 告警、工单、客服、协议签署、通知 outbox、审计、请求追踪和分布式限流。
- 微信支付 APIv3 官方 SDK 下单、验签解密、退款与回调，支付/退款主动查单恢复；官方接收方登记、逐笔分账、幂等补偿、退款分账回退和对应双式账务；设备密钥加密分发与轮换。
- 微信订阅消息授权、模板映射、access token 共享缓存、outbox 发送与指数退避重试。

## 本轮本地验证（2026-09-30）

- 后端 `clean verify`：95 项测试全部通过，零失败、零跳过；采用一次性真实 PostgreSQL 18.6，运行账号不能绕过 RLS，全部 12 个迁移通过。
- 实际 HTTP 测试覆盖超级管理员首次改密、旧会话撤销、租户开通、岗位分配、跨租户/越权拒绝、三级组织、12 个端口、费率绑定、签名充电码和管理员安全停充。
- 真实数据库验证充电幂等/并发、开始/计量/停止/计费、迟到启动安全停止、支付退款入账幂等、原号原参数恢复、钱包冻结余额保护和双向账单差异。
- 管理端 14 项、小程序 17 项行为测试通过；Web 构建和 47 个小程序源文件、9 个页面检查通过。交互按 UI/UX 规则补充危险操作确认、真实结果确认和身份切换时清理缓存。
- 运维脚本通过 Windows PowerShell 5.1 语法、配置和恢复前安全检查；真实数据库验证历史权限升级清理，包括不同授予者遗留的迁移角色授权。
- 后端已解析的 142 个第三方依赖经 OSV 查询没有返回已知漏洞，前端 `npm audit` 没有返回已知漏洞；该结论仅对应此次版本与查询时点。

上述测试仅在隔离环境创建验收夹具。HTTP 测试替换了 NATS/Valkey 外部连接，资金测试替换了支付机构边界；并不是实际支付、实际设备、容器网络或备份恢复演练。本机没有 Docker，新增的 Docker CI 验收必须另外核实结果。不能据此将全部商业功能标记为已完成。

## 尚未交付的软件能力

以下是软件范围缺口，补齐资质或填写 `.env` 不会自动实现，不能把它们写成“只待配置”：

| 能力 | 当前实现与限制 |
|---|---|
| 支付宝 | 尚未实现支付宝小程序、登录、支付与退款适配；渠道无关接口仅为后续接入基础 |
| 线上钱包 | 已有余额查询与受审计人工更正，没有线上充值、余额支付或提现链路 |
| 自动税务开票 | 已有发票申请及真实开票凭证录入，没有自动调用税务或第三方开票平台 |
| 自动账单采集 | 日对账接收完整销售账单导入，并验证缺失、重复、金额和商户归属；没有自动下载支付机构退款账单 |
| 首单支付保障 | 当前按后付费流程计费；欠费用户禁止再开新单，但首次交易仍可能坏账，没有押金冻结或免密自动扣款 |

上线时必须按上述已实现范围展示功能、签订运营约定并进行验收；如果经营方案依赖任一缺口，需先实现该软件链路再开放相应业务。

## 外部材料和实机验收

受外部资质、凭据、真实设备或生产基础设施约束，正式收款和接入真实设备前仍必须全部通过：

- 真实桩协议适配、断网续传、命令 ACK、乱序/重复消息和断电恢复测试。
- 微信支付商户验收、回调白名单/验签、退款、日账单、接收方关系、获批分账比例、部分失败及退款回退的真实环境验收；所有接收方必须是支付机构审核通过的真实商户，禁止用个人收款码替代。
- 平台、一级/二级/三级经营主体的合同、开票、收入确认和纳税口径由财税与法律顾问审核。支付机构分账记录只证明资金分配，不能作为免税依据。
- 管理员角色矩阵复核、密钥托管、审计留存、个人信息合规和账号恢复流程评审；临时密码只能通过独立安全渠道交付，不能写入工单、普通聊天或日志。
- 验收超级管理员凭据保管、员工离职停用、密码重置交付、角色变更审计和会话即时撤销；内置数据库身份不依赖 Keycloak。
- PostgreSQL 主从/备份恢复演练，Valkey 与 NATS 高可用故障切换演练。
- 默认 Compose 已分离 PostgreSQL 初始化、迁移、业务运行账号，运行账号禁止超级用户及 `BYPASSRLS`；NATS 已使用随机 token 鉴权。单机桥接内网不对公网发布消息端口，多机迁移时还需 NATS TLS、细分发布/订阅权限与 JetStream 多副本。
- 峰值容量压测、72 小时稳定性测试、SAST/SCA/镜像扫描、渗透测试和依赖许可证复核。
- 灰度发布、数据库向前兼容迁移、回滚预案、监控告警、SLO 与值班响应流程。

首台实体桩应先在隔离验收环境跑完整闭环，不直接处理真实资金。通过验收后再切换生产商户和正式域名。
`ops/compose.local.yaml` 保持空库并使用真实鉴权逻辑，填写 `PUBLIC_HOST` 后自动启用可信 HTTPS 入口，可用于首批单机生产发布。数据库和消息/诊断端口只绑定回环；设备网关只有提供真实 mTLS 材料后才启动。配置和发布步骤见 [Docker 部署](docker-local.md)。已提供数据库、Valkey、NATS 和加密密钥来自同一停机时点的一致性备份/恢复流程；正式放行前仍必须在隔离环境恢复演练。这个版本的默认部署是单机，不提供主机级自动故障切换。

CI 新增实际 Docker 构建和启动验收：空业务库启动、首次改密、超级管理员开通租户/账号、普通账号拒绝平台管理接口、运行数据库账号无 RLS 绕过权限、NATS 匿名连接拒绝，以及一致性备份恢复后的账户和租户保留。仅隔离 CI 会创建验收记录，生产启动不会写任何测试业务数据。本机已经使用真实隔离 PostgreSQL 验证角色初始化、非超级用户迁移与 RLS，但没有 Docker 的机器仍不能据此宣称已通过容器实机、支付机构或真实桩验收。
