# V2 架构

## 原则

V2 采用“模块化单体核心 + 独立设备网关”的起步形态。交易一致性优先的租户、资产、订单、计费、支付、
账务和运营能力留在同一核心进程与数据库事务中；长连接和协议解析独立部署，避免设备流量影响用户 API。
达到明确的组织或容量边界后，再从模块边界拆分服务，不预先承担微服务分布式事务成本。

## 运行链路

1. 微信小程序通过平台适配层完成登录，业务 API 只接收平台内部身份；支付宝后续实现同一适配契约。
2. 客户端只提交幂等键和充电口；租户与客户来自已验证令牌，费率来自充电口当前配置，避免越权指定身份或价格。数据库锁定充电口并原子写入订单、会话、设备命令和 outbox。
3. 异步发布器把设备命令投递至 NATS JetStream；设备网关向在线连接下发并持久化 ACK。
4. 设备上报先通过双向 TLS、消息 HMAC、时间窗和 Valkey nonce 检查，再进入事件流。
5. 会话结束后，可信计量样本驱动计费；支付回调验签且幂等，账务以借贷平衡分录入账。

微信支付通道使用官方 APIv3 SDK生成小程序 JSAPI 参数，并对支付/退款回调的原始报文验签和解密。商户配置按租户
读取，私钥、APIv3 密钥及平台公钥只通过 `env:PREFIX` 秘密引用解析，不写入数据库或日志。

## 数据隔离

所有租户业务表都带 `tenant_id`。API 从已验证 JWT 的 `tenant_ids` 声明校验请求头，数据库事务设置
`app.tenant_id`，PostgreSQL RLS 再次强制过滤。后台任务必须按消息携带的可信租户标识开启独立事务。
生产数据库必须将迁移账号与运行账号分离：迁移账号拥有 DDL 权限，应用使用非超级用户、非表所有者账号，
且不得授予 `BYPASSRLS`。本地 Compose 为方便初始化使用单一超级用户，只允许用于开发环境，不能照搬到生产。
租户开通走仅允许 `SCOPE_internal` 的内部接口，租户、首个管理员和审计记录在同一事务创建；相同租户的重试会幂等修复管理员成员关系，租户标识或编码冲突则拒绝处理；公网后台不提供
“抢占首个管理员”的匿名入口。
自托管身份模式下，后端还会对初始租户执行受限的登录时校正：验签 JWT 包含初始租户声明，并且具有 `admin` 身份角色或匹配配置中的唯一初始管理员用户名时，才能以令牌中的真实 `sub` 创建缺失的首个 `TENANT_ADMIN` 关系并写入审计。外部 OIDC 模式不会启用该行为，已停用的成员关系也不会被自动恢复。

## 扩容

- 核心 API 无状态水平扩容；写一致性由 PostgreSQL 事务、唯一约束和行锁保证。
- 设备网关按连接数水平扩容；NATS 将命令广播到各网关，持有目标连接的实例完成下发。Valkey 保存防重放
  nonce 与加密设备凭据，事件和命令由 JetStream 解耦。
- 计量表按月或按周分区；超过单库安全容量后按租户/区域分片。
- PostgreSQL、Valkey、NATS 在正式生产使用托管或三节点高可用，不与应用争抢同一台主机资源。
- NATS 生产集群必须启用账号权限、TLS 与 JetStream 副本；设备凭据应存入 KMS/密钥服务并支持轮换，不能使用环境变量明文清单长期管理。
- 当前设备共享密钥由核心服务随机生成、AES-256-GCM 加密后写入 Valkey，网关按需解密并短时缓存；加密主密钥必须由生产秘密管理系统注入并定期轮换。

## 平台前端

管理端采用 Vue 3 + TypeScript。微信端采用原生小程序，保持零运行依赖和最小包体；支付宝端后续使用独立薄壳。
两个小程序共用同一 OpenAPI 契约、业务状态定义和测试用例，登录、支付、手机号、订阅消息、地图等能力放在各自
`platform` 适配层中。当前微信端保持原生实现，以减少运行时和构建供应链体积。
